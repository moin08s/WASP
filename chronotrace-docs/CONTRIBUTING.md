# Contributing to ChronoTrace

Thank you for helping improve digital forensics tooling. ChronoTrace automates six core
forensic objectives — file metadata extraction, system artefact extraction, timestamp
extraction, chronological activity timeline reconstruction, SHA-256 evidence integrity,
and structured investigation reporting. This document explains how to propose changes, the
standards we hold contributions to, and the forensic-specific rules that apply to this
project.

---

All participation is governed by [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).

## 2. Ground rules specific to forensic software

Because ChronoTrace output may be used as evidence, contributions are held to a higher bar
than typical application code:

1. **Correctness over features.** A parser that is 99% right is dangerous. If you cannot
   verify a format against a specification or a known-good reference, do not ship it —
   file an issue instead.
2. **Never modify evidence.** No code path may open an evidence source for writing. The
   write-guard is a hard boundary; PRs that weaken it will be rejected.
3. **Determinism is a feature.** Any new output must be reproducible. Do not depend on
   dict iteration order, thread scheduling, `time.time()` in output, or the analysis
   host's locale/timezone.
4. **Provenance is mandatory.** Every emitted event must be traceable to a source record
   (file, offset, record ID). Events without provenance must be rejected by the parser.
5. **Document confidence.** If a timestamp is inferred (e.g. from a log line without an
   explicit year), the parser must set `confidence < 1.0` and explain why in `rationale`.
6. **No silent data loss.** If a record cannot be parsed, emit a `ParseWarning` record
   into `derived/<plugin>.warnings.jsonl` rather than dropping it.

## 4. Branching and commits

- Branch from `main`: `feat/evtx-template-cache`, `fix/usn-sparse-boundary`.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):

text

```
feat(plugins/evtx): cache BinXml templates per chunk

Reduces EVTX parsing time by ~40% on 2 GB logs by memoizing
template resolution within a chunk.
```

Scopes: `core`, `cli`, `timeline`, `integrity`, `report`, `plugins/<name>`, `docs`, `ci`.

## 5. Pull request requirements

Every PR must:

- □ 

  Pass `pytest`, `ruff`, `mypy --strict`, and `bandit`.
- □ 

  Include tests (see [docs/TESTING.md](https://docs/TESTING.md)).
- □ 

  Update `CHANGELOG.md` under `[Unreleased]`.
- □ 

  Update relevant docs in `docs/`.
- □ 

  For new plugins: include a plugin manifest, capability declaration, and at least one
  real-world sample fixture with a documented provenance (public corpus, synthesized,
  or donated with permission).
- □ 

  For schema changes: bump `SCHEMA_VERSION` and add a migration note.
- □ 

  Declare whether output is affected (a "no output change" assertion is required for
  pure refactors).

Use the [PR template](https://.github/PULL_REQUEST_TEMPLATE.md).

## 6. Test fixtures and evidence

**Do not commit real case data.** Fixtures must be one of:

- Publicly available forensic corpora (e.g. Digital Corpora, NIST CFReDS) — record the
  source and license in `tests/fixtures/<name>/PROVENANCE.md`.
- Synthesized fixtures generated by `tools/make_fixture.py` — commit the generator, not
  the binary, where feasible.
- Donated samples with written permission from the donor, anonymized.

Fixtures containing personal data must be redacted or synthesized. CI rejects commits
that match the PII scanner ruleset.

## 7. Style

- Python 3.11+, `ruff format`, line length 100.
- Type hints everywhere; `mypy --strict` on `chronotrace/`.
- No `print()` in library code — use the `chronotrace.logging` structured logger.
- Prefer `pathlib` over `os.path`.
- Dataclasses/Pydantic models over raw dicts for structured data.
- All public functions require docstrings (Google style).

---

## 8. Adding a new artefact plugin (short version)

1. `mkdir chronotrace/plugins/<name>` with `__init__.py`, `plugin.py`, `manifest.toml`.
2. Subclass `chronotrace.plugin.ArtifactPlugin`.
3. Declare `name`, `version`, `capabilities`, `input_globs`, `applies_to`.
4. Implement `parse(source: EvidenceView) -> Iterator[Event]`.
5. Register in `pyproject.toml` under `[project.entry-points."chronotrace.plugins"]`.
6. Add tests + fixture provenance.

Full guide: [docs/PLUGIN_DEVELOPMENT.md](https://docs/PLUGIN_DEVELOPMENT.md).

## 9. Reporting bugs

Use the [bug report template](https://.github/ISSUE_TEMPLATE/bug_report.md). Include:

- ChronoTrace version (`chronotrace --version`), OS, Python version.
- The exact command and config (redact case-identifying data).
- Expected vs. actual output.
- If possible, a minimal synthesized fixture that reproduces the issue.

**Security issues** go to `security@chronotrace.example` per [SECURITY.md](https://security.md/),
not the public tracker.

---

## 10. Review process

- One maintainer approval required for docs/tests; two for core, integrity, or plugin
  contract changes.
- Reviewers specifically check: evidence write-guard, determinism, provenance, confidence
  handling, and changelog entry.
- Maintainers may request a reference implementation comparison for format parsers.

---

## 11. Recognition

Contributors are listed in `CONTRIBUTORS.md` (generated from git history) and, with
